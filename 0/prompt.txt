## PR
**https://github.com/scottdensmore/my-first-commit/pull/164** — `fix(api): bound search bursts per client`, ready for review (not draft), `Closes #151`, references #106 without closing it.

## Threshold: 30 searches per rolling 60 seconds, per client
Counted only for searches that can still reach GitHub — a cache hit is free. Justification, which is in the PR body and `docs/production.md`: sustained, 30/min is one distinct valid GitHub handle typed every two seconds for a full minute; a visitor clicking every recent-search shortcut they have stored produces five requests and then stops to read one. It is also the documented authenticated GitHub search ceiling — I verified against current GitHub docs rather than the brief: **30 requests/minute authenticated** for search endpoints other than code search, **10/minute unauthenticated** (code search is 10/min authenticated; commit search is the 30 tier). So a client past the bound is on its own able to spend the entire shared per-minute allowance. Per-client is what lets the number sit that far above human pace without a traffic estimate.

Presented throughout as reducing the cost of abuse, never as a quota guarantee: 30 × instances, resets on cold start, cannot defend a 30/min ceiling; the cache and #150's coalescing are named as what actually cuts upstream load, and a Vercel Firewall rule is named as where a real global ceiling would go.

## Retained in memory
Per client, until it has been quiet longer than the 60s window: a **salted SHA-256 hash** of the forwarded address, plus the timestamps of that client's searches inside the current window (at most 30). Nothing else. The username never reaches the limiter — `app/commitSearchRateLimit.ts` is handed an opaque key by `app/searchClientKey.ts`, so it has nothing else to store or log; the refusal event `commit_search_rate_limited_client` carries only `limit` and `windowMs`. Salt is 32 random bytes per process, never persisted. A memory dump would reveal salt + hashes + timestamps: enough to confirm whether an *already-suspected* address was active in the last minute, not enough to read addresses out, correlate across instances or restarts, or learn anything about what was searched.

## Bounding the map
Idle clients dropped as the window passes them, plus a hard cap of 500 clients with least-recently-active eviction. Tested with 5,000 distinct keys.

## Spoofed forwarded header
Key comes from `x-vercel-forwarded-for`, falling back to `x-forwarded-for`. Vercel overwrites `x-forwarded-for` from the connecting socket to prevent spoofing and sets `x-vercel-forwarded-for` itself, so on this deployment neither is attacker-controlled; the preference keeps that true behind another proxy. Behind a proxy that forwards verbatim, a spoofer **can** split their own traffic across fabricated addresses (weakening the limit to the cost of forging headers) and **can** spend a known client's allowance to refuse them for up to one window on one instance. They **cannot** exhaust memory (idle eviction, cap, and over-long values truncated rather than rejected so an absurd value can't buy an unlimited lane), **cannot** deny service via eviction (eviction only forgets, which refills an allowance — pinned by a test), and learn nothing about other clients or searches.
