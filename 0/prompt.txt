## New findings

**1. should-fix — `/home/scottdensmore/Developer/scottdensmore/my-first-commit/app/home/SearchResults.tsx:88` — the retry button's boundary fails WCAG 1.4.11 (2.07:1), and nearly vanishes while it is working.**
The button is `bg-white` on the section's `bg-amber-50`: the fill contrast is 1.04:1, so the border is the only thing that identifies the control. `border-amber-500` (`#f59e0b`) on `amber-50` (`#fffbeb`) is **2.07:1**, below the 3:1 required for a control's visual boundary. `aria-disabled:opacity-50` then blends the border to **1.46:1** during the pending state — the button all but disappears at the exact moment the user is watching it. Low-vision and bright-screen users lose the affordance.
*Fix:* `border-amber-700` (4.84:1 on `amber-50`) or at minimum `border-amber-600` (3.07:1, no margin). `amber-700` also sits comfortably with the existing `text-amber-900`. The app's other secondary buttons have similarly thin borders, but they sit on white where the surrounding contrast carries them; this one does not.

**2. should-fix — `/home/scottdensmore/Developer/scottdensmore/my-first-commit/app/home/SearchResults.tsx:88,90` — the "Searching again..." label, the only progress feedback in this view, renders at 2.60:1.**
`aria-disabled:opacity-50` composites `text-amber-900` on white over `amber-50`, giving `#bc987d` on `#fffdf5` = **2.60:1**, against a 4.5:1 requirement. WCAG's inactive-component exemption is a poor fit: this is a transient pending state whose label is the message, not an inert control. It matters more than usual because the page-level `Searching GitHub for ...` block at `app/page.tsx:188` is suppressed once `result` exists, so this label is the *entire* progress signal for a retry. Note also that `!lastSearchedUsername` is unreachable inside this component (`SearchResults` only renders after a search that set it), so `isRetryDisabled` is always exactly `isPending` — the dimmed state is never the "truly inactive" case the opacity was meant for.
*Fix:* drop `aria-disabled:opacity-50` and express the pending state with contrast-safe styling instead, e.g. `aria-disabled:bg-amber-50 aria-disabled:border-amber-300` plus the existing `aria-disabled:cursor-not-allowed`. The label change plus `aria-disabled` already carries the meaning.

**3. should-fix — `/home/scottdensmore/Developer/scottdensmore/my-first-commit/app/page.tsx:210-220` (with `app/home/searchExecution.ts:59`) — a failed retry throws away the partial result the user was reading.**
"Search again" is the first control this app has ever placed inside a successful result view that re-issues a search. `runCommitSearch` calls `setResult(data)` unconditionally, so if the retry comes back rate-limited, timed out, or unavailable, `result.found` flips to `false`: `SearchResults` unmounts, the hero and search form return, and the ten commits the visitor was looking at are gone, replaced by an error box. GitHub's commit-search limit is shared across all users of the app's token, so this is reachable, and a slow search that returned `incomplete_results` is precisely the kind that gets retried. Recovery exists ("Try again" re-runs `lastSearchedUsername`), but the user is punished with total data loss for taking the affordance the UI offered.
*Fix:* keep the last `found` result when a retry from the results view fails, and render the failure inside the amber callout — e.g. thread a `retryError` message through `SearchResults` and swap the button row for `"That retry failed: &lt;message&gt;"` plus the button, leaving the commits on screen. **4. polish — `/home/scottdensmore/Developer/scottdensmore/my-first-commit/app/home/SearchErrorState.tsx:37-39,68` — the same GitHub condition gets two different visual languages and two different button labels.**

### should-fix — `/home/scottdensmore/Developer/scottdensmore/my-first-commit/scripts/e2e-server-identity.mjs:103-114`: "not a timeout" is not the same as "nothing listening"

The catch treats every non-timeout rejection as a free port. Real `fetch` rejections do not distinguish themselves by `name`; they distinguish by `cause.code`. I measured both on this Node:
